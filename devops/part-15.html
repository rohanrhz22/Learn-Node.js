🚀 Deployment Strategies & GitOps

Release without downtime, limit blast radius, and make Git the single source of truth for what's running.

Why strategy matters The Risk of Deploys

A naive deploy stops the old version and starts the new one — causing downtime, and if the new version is broken, an instant outage for everyone.

  • Goal 1 — zero downtime during release.
  • Goal 2 — limit how many users a bad release can affect.
  • Goal 3 — roll back fast and safely.
  • Goal 4 — validate the new version with real traffic first.
📌
Deployment strategies trade speed, cost and safety. The right choice depends on how risky a change is and how critical the service is.

The main patterns Deployment Strategies

StrategyHow it works
RollingReplace instances a few at a time (K8s default)
Blue-GreenRun two full environments; switch traffic at once
CanarySend a small % of traffic to the new version first
Feature flagsShip code dark, enable per-user at runtime
Blue-green — flip traffic instantly, roll back by flipping back.
Canary — gradually shift traffic while watching metrics.

Trade-offs Choosing a Strategy

StrategyProsCons
RollingSimple, no extra costSlow rollback, mixed versions
Blue-GreenInstant switch & rollbackDouble the infrastructure
CanarySmallest blast radiusNeeds good metrics & routing
FlagsDecouple deploy from releaseFlag debt to manage
💡
Combine them: deploy with rolling updates, expose features behind flags, and canary the riskiest changes. They're complementary, not exclusive.

Git as the source of truth GitOps

GitOps stores the desired state of your infrastructure and apps in Git. An agent in the cluster continuously reconciles reality to match the repo.

The cluster pulls from Git — no one pushes to it directly.
  • Declarative — the repo describes the whole system.
  • Pull-based — the cluster reconciles itself from Git.
  • Auditable — every change is a reviewed commit.
  • Self-healing — manual drift is reverted automatically.
📌
In GitOps you don't run kubectl apply by hand. You merge a PR; the agent (Argo CD / Flux) applies it for you.

Argo CD & Flux GitOps in Practice

Tools like Argo CD and Flux watch a Git repo of manifests and keep the cluster in sync.

# An Argo CD Application points at a repo path
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: web }
spec:
  source:
    repoURL: https://github.com/team/manifests
    path: apps/web
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: web
  syncPolicy:
    automated: { prune: true, selfHeal: true }
⚠️
With selfHeal on, hand-editing the cluster is pointless — the agent reverts it within seconds. Make the change in Git, the right way, every time.
