🧱 Build, Test & Artifacts

Turn source code into a tested, versioned, immutable package you can deploy anywhere.

Source → package The Build Step

A build transforms source code into something runnable: a compiled binary, a JS bundle, a JAR, or a container image.

The build pipeline produces a deployable artifact.
# Examples across ecosystems
npm run build          # JS → dist/
mvn package            # Java → target/app.jar
go build -o app ./...  # Go → binary
docker build -t app .   # → container image
📌
A good build is reproducible: the same source always produces an equivalent artifact, independent of the machine running it.

Confidence, fast The Test Pyramid

Balance test types for speed and confidence — many fast tests, few slow ones:

The test pyramid — push most testing down to the cheap, fast layer.
TypeTestsSpeed
UnitOne function in isolationMilliseconds
IntegrationModules + DB/queue togetherSeconds
End-to-endThe whole app like a userMinutes
💡
Add linting and static analysis as the very first checks — they're instant and catch whole classes of bugs before tests even run.

Build once, deploy many Artifacts

An artifact is the immutable output of a build — a versioned file or image you store and deploy. Build it once and promote that exact artifact through every environment.

  • Immutable — never edit an artifact; build a new version.
  • Versioned — every artifact has a unique tag.
  • Traceable — you can map an artifact back to its commit.
⚠️
Rebuilding separately for staging and prod is an anti-pattern — you can't guarantee they're identical. Promote the same artifact you already tested.

Where artifacts live Registries & Versioning

A registry / repository stores artifacts: container images (Docker Hub, ECR, GHCR), packages (npm, PyPI, Maven), or generic files (Artifactory, Nexus).

# Tag and push a container image
docker build -t ghcr.io/team/app:1.4.0 .
docker push ghcr.io/team/app:1.4.0

# Publish an npm package
npm version patch
npm publish

Use semantic versioning — MAJOR.MINOR.PATCH:

BumpWhen
MAJORBreaking change
MINORNew, backward-compatible feature
PATCHBug fix
💡
Avoid deploying the latest tag to production — it's a moving target. Pin a specific version (1.4.0) so deploys are deterministic.

Faster pipelines Caching & Speed

Builds repeat the same work — cache it to save minutes per run:

# Cache dependencies in GitHub Actions
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
  • Dependency cache — reuse downloaded packages.
  • Layer cache — Docker reuses unchanged layers (Part 8).
  • Parallel jobs — run independent stages at once.
📌
A cache key based on a lockfile hash means the cache is reused while dependencies are unchanged, and rebuilt automatically when they change.

Practice

  3. Add a dependency cache and measure the build-time improvement.
