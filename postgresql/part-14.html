🔒 Transactions & Concurrency

Group changes atomically and keep data correct when many clients write at once.

Concept ACID & Why Transactions

A transaction groups multiple statements into one all-or-nothing unit. PostgreSQL guarantees ACID:

PropertyMeaning
Atomicityall statements succeed, or none do
Consistencyconstraints always hold
Isolationconcurrent txns don’t corrupt each other
Durabilitycommitted data survives a crash
📌
The classic example: transferring money. Debit one account and credit another — both happen or neither does.

Core BEGIN, COMMIT, ROLLBACK

Wrap statements between BEGIN and COMMIT. If anything goes wrong, ROLLBACK undoes the whole block.

BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;       -- both updates become permanent together

BEGIN;
  DELETE FROM orders WHERE id = 5;
ROLLBACK;     -- changed my mind: nothing happened
Everything between BEGIN and COMMIT is one atomic unit; ROLLBACK discards it.
⚠️
If the connection drops mid-transaction, Postgres automatically rolls back — you never get a half-applied transfer.

Partial rollback Savepoints

Savepoints let you roll back part of a transaction without abandoning the whole thing.

BEGIN;
  INSERT INTO logs (msg) VALUES ('start');
  SAVEPOINT before_risky;
  INSERT INTO logs (msg) VALUES ('risky');
  ROLLBACK TO before_risky;     -- undo only the risky insert
  INSERT INTO logs (msg) VALUES ('safe');
COMMIT;
💡
Useful inside long transactions or procedures where one optional step may fail but you want to keep the rest.

Concurrency control Isolation Levels

Isolation controls what one transaction sees of others’ uncommitted/concurrent work. Higher levels prevent more anomalies at some cost.

LevelPrevents
Read Committed (default)dirty reads
Repeatable Read+ non-repeatable reads
Serializable+ phantoms; acts as if serial
BEGIN ISOLATION LEVEL SERIALIZABLE;
  -- ... reads and writes ...
COMMIT;
📌
Postgres’ default Read Committed is enough for most apps. Use SERIALIZABLE for critical invariants — be ready to retry on serialization failures.

Contention Locks & Deadlocks

Writes take row locks so two transactions can’t change the same row at once. A deadlock happens when two txns each wait on a row the other holds.

Postgres detects deadlocks automatically and cancels one transaction with an error.
💡
Avoid deadlocks by always acquiring locks in a consistent order (e.g. update accounts by ascending id) and keeping transactions short.

Explicit locking SELECT ... FOR UPDATE

Lock the rows you read so no one else can modify them until you commit — the basis of safe read-modify-write.

BEGIN;
  SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- lock it
  -- ... compute new balance in app ...
  UPDATE accounts SET balance = 50 WHERE id = 1;
COMMIT;

-- skip rows already locked (job-queue pattern):
SELECT * FROM jobs WHERE status='queued'
ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;
📌
FOR UPDATE SKIP LOCKED is the standard recipe for building concurrent worker queues in Postgres.

Practice

  1. Wrap two related UPDATEs in a transaction and COMMIT.
  2. Start a transaction, DELETE a row, inspect it, then ROLLBACK.
  3. Use SELECT ... FOR UPDATE to lock a row, then update it safely.
