🏛️ Tuning, Scaling & Best Practices

Take a working database to production: fast, healthy and scalable.

Make it fast Query Tuning Workflow

Optimization is measurement-driven. Find the slow query, read its plan, fix the cause, verify.

Always confirm a change actually helped — intuition about performance is often wrong.
  • Enable pg_stat_statements to find your most expensive queries.
  • Look for Seq Scan on large tables and high actual rows vs estimate.
  • Add the right index, rewrite the query, or ANALYZE to refresh statistics.
💡
pg_stat_statements is the single best tool for “which queries should I optimize?” — enable it first.

Housekeeping VACUUM, ANALYZE & Bloat

PostgreSQL’s MVCC leaves dead row versions after updates/deletes. VACUUM reclaims them; ANALYZE refreshes planner statistics.

VACUUM ANALYZE orders;     -- clean + update stats
VACUUM FULL orders;        -- rewrites table, reclaims disk (locks!)

-- check bloat / last autovacuum:
SELECT relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;
⚠️
Autovacuum runs automatically — don’t disable it. Tune it for high-write tables. VACUUM FULL takes an exclusive lock, so schedule it during maintenance windows.

Server tuning Configuration Essentials

A handful of postgresql.conf settings dominate performance. Defaults are conservative — size them to your hardware.

SettingRough guidance
shared_buffers~25% of RAM
effective_cache_size~50–75% of RAM
work_memper-sort; raise for big queries
maintenance_work_memspeeds VACUUM/index builds
max_connectionskeep modest; use a pooler
💡
Try a calculator like PGTune for sane starting values, then verify with real workload metrics. Change one thing at a time.

Divide & conquer Partitioning Large Tables

Declarative partitioning splits one huge table into smaller physical pieces by range, list or hash — the planner prunes irrelevant partitions automatically.

CREATE TABLE events (
    id bigint, created_at date, body jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
📌
Partitioning shines for time-series data: queries hit only the relevant month/year, and dropping old data is an instant DROP TABLE on a partition.

Going bigger Replication, Pooling & Scaling

Scale reads and add resilience with replicas; protect the server with a connection pooler.

  • Streaming replication — hot standbys for failover and read scaling.
  • Read replicas — send reporting/read traffic off the primary.
  • Connection pooling — PgBouncer multiplexes thousands of clients onto few connections.
  • Sharding/extensions — Citus for horizontal scale-out when one node isn’t enough.
⚠️
Postgres connections are heavyweight. Never point thousands of app clients straight at the DB — put PgBouncer in front.

Ship it Production Best-Practice Checklist

  • Primary key on every table
  • Indexes for real WHERE/JOIN columns
  • Constraints enforce integrity (not just app code)
  • timestamptz for all timestamps
  • Migrations in version control
  • Automated, tested backups + PITR
  • Least-privilege roles & SSL
  • Autovacuum healthy, pg_stat_statements on
  • Connection pooler in front
💡
Treat the schema as code: review migrations, test on a staging copy, and monitor query stats continuously.

Capstone Project

  1. Design a small app schema (users, items, orders) with keys, constraints and indexes.
  2. Add a view, a trigger for updated_at, and a window-function report query.
  3. Set up a readonly role, take a pg_dump backup, and restore it to verify.
  4. Run EXPLAIN ANALYZE on your heaviest query and tune it with an index.
