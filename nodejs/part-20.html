Concept Monolith vs Microservices

A monolith is one codebase doing everything — simple to start. Microservices split features into small, independently deployable services.

Each microservice owns one domain and its own database, communicating over the network.
MonolithMicroservices
Start speedFastSlower
ScalingAll-or-nothingPer-service
DeployOne unitIndependent
ComplexityLowHigh (networking, ops)
📌
Start as a well-structured monolith. Split into services only when teams or scaling needs demand it — don't add complexity early.

Pattern Service Communication

Services talk in two main ways:

  • Synchronous — direct HTTP/gRPC calls; the caller waits for a reply. Simple, but couples services and propagates failures.
  • Asynchronous — messages via a queue; the sender doesn't wait. Resilient and decoupled.
Synchronous calls are easy but create tight coupling and cascading failures.
💡
Use sync calls for instant reads, and async messages for work that can happen in the background (emails, invoices, notifications).

Tool Message Queues

A queue holds jobs so a producer can hand off work and a consumer processes it later — smoothing spikes and surviving restarts.

Producers add jobs; workers pull and process them independently.
// BullMQ (Redis-backed) — add a background job
const { Queue } = require("bullmq");
const emailQueue = new Queue("emails", { connection: { host: "127.0.0.1" } });

await emailQueue.add("welcome", { to: "asha@x.com" });
// worker.js — process jobs separately
const { Worker } = require("bullmq");

new Worker("emails", async (job) => {
  await sendEmail(job.data.to); // retried automatically on failure
}, { connection: { host: "127.0.0.1" } });
📌
Queues give you retries, rate control and durability. The web request returns instantly while the heavy work happens in a worker.

Intro GraphQL — An Alternative to REST

GraphQL lets clients request exactly the fields they need from a single endpoint — solving over- and under-fetching common in REST.

# a query: ask for only what you need
query {
  user(id: 1) {
    name
    posts { title }
  }
}
// minimal Apollo Server
const { ApolloServer } = require("@apollo/server");

const typeDefs = `#graphql
  type User { id: ID!, name: String!, posts: [Post!] }
  type Post { title: String! }
  type Query { user(id: ID!): User }
`;

const resolvers = {
  Query: { user: (_, { id }) => User.findById(id) },
};

const server = new ApolloServer({ typeDefs, resolvers });
RESTGraphQL
EndpointsManyOne
Data shapeFixed per routeClient-defined
Over-fetchingCommonAvoided
📌
GraphQL isn't “better” than REST — it's a trade-off. REST is simpler; GraphQL shines for complex, nested, client-driven data.
